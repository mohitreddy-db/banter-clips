01 The product

What BanterClips actually is

A user types a sports opinion (10–280 characters), picks a sport, a tone and a length. The system writes a shot-by-shot comedy script, casts real athletes, generates a photoreal keyframe for each shot, animates each keyframe into a talking clip, joins them, burns in captions, and hands back a 9:16 MP4 they can publish to Instagram — without leaving the app.

The one-line promise from BRD.md: any sports take becomes a post-ready video, no editing. Phase 1 is a private beta with two plans.

The four inputs

  • Take — 10–280 chars, the user's opinion
  • Sport — NBA / NFL / Soccer / MLB
  • Tone — Funny / Savage / Hype / Bold
  • Length — 10s / 15s / 30s >15s = Creator

Plus resolution: 720p everyone, 1080p Creator-only.

The two plans BR-15

The rule that shapes everything

Free is deliberately publish-only. Every free clip that lands on Instagram carries the watermark and markets the product. The locked download button is the upgrade prompt — it isn't hidden, it's the sales surface.

06 Auth

Two identity systems, bridged once

browser ── email+password / Google / magic link ──▶  Supabase Auth
browser ── supabase access_token ──────────────────▶  POST /auth/supabase
                                                        │
   backend verifies the token at {SUPABASE_URL}/auth/v1/user
   finds-or-creates the local users row (linked by supabase_uid)
                                                        │
                              └─▶ issues OUR own 30-day HS256 JWT
                                  used as Bearer on every other endpoint

Sessions are stateless — nothing is stored server-side. The token payload is just {sub, iat, exp}; get_current_user in deps.py decodes it and loads the user. Rotating JWT_SECRET signs everyone out globally.

Details worth knowing

  • Blocked users learn nothing. A blocked account gets the identical generic 401 that a bad token gets, at both sign-in and on every request. From outside it looks like a login that won't stick.
  • Admin is an email allow-list, unioned from the ADMIN_EMAILS env bootstrap (never removable) and a DB-managed list cached 30s in-process. Non-admins get 404, not 403 — they shouldn't learn the admin surface exists.
  • Dev magic-link. With DEV_MODE=true, POST /auth/request-link returns the token in the response body — sign in as any email, no mailbox, no Supabase. Returns 404 when DEV_MODE=false.
  • Google prompts for account selection every time (prompt: "select_account") — without it, Google silently reuses the last account with no way to switch.
  • Password recovery is detected from the URL hash before supabase-js consumes it, so a recovery link always lands on /reset-password regardless of where the redirect allow-list dropped the browser.

Schema migrations

There is no Alembic. db_migrate.py runs on every API and worker boot: a hardcoded list of ALTER TABLE … ADD COLUMN IF NOT EXISTS plus a rebuild of the clips_status_check constraint from CLIP_STATUSES. 09 The pipeline

Take → MP4, stage by stage

This is app/video/ — twenty modules and the most interesting code in the repo. Entry points: generate_video() (pure, no DB) and run_clip_job(clip_id) (drives a Clip row).

The one rule

A job always produces a video. Missing take, unknown sport, no API keys, a model returning garbage, a scene that won't render — each degrades rather than failing the job. Only two things are fatal: no ffmpeg, or not a single usable scene. generate_video never raises; it returns a Result with warnings attached.

Stage by stage

0  Enhance — enhancer.py

Quality is decided before money is spent. One LLM call sharpens the take while keeping the user's stance ("lakers bad" → "Every time the Lakers throw up a brick you can hear Shaq groaning"), extracts subjects and teams, and flags genuine ambiguity. Then it returns Question objects only for gaps that measurably change output: a take too thin to build beats from, an unknown cast name, two teams with no clear lead, unstated tone/length/look. Every question carries a default, so silence is always a valid answer and nothing ever blocks.

Style is a fixed preset, never model-authored. Three photographic looks — broadcast, cinematic, gritty. A free-form style line per job is not repeatable; allowing one is how a video once came out half photoreal, half cartoon.

1–2  Resolve & focus — defaults.py focus.py

defaults.resolve() fills every missing input — infers the sport, snaps duration, replaces a too-short take. Nothing downstream ever sees a null. focus.py then classifies the take as player / team / matchup / generic from catalog mentions, and that classification drives the colour palette, the venue list, and the casting order.

3  Plan — planner.py

Three layers, tried in order, so a plan always comes back:

  1. Ask the model for structured JSON (gpt-4.1, JSON mode, 16k token ceiling).
  2. Repair whatever came back — fill missing fields, force the scene count, scale shot lengths to hit the target duration, enforce one-speaker-per-scene, trim over-long lines, force one shared venue across every shot.
  3. If the model is unreachable or unparseable, build a deterministic template plan instead.

Layer 2 is the important one: "models return nearly-right JSON far more often than they return nothing, and rejecting a nearly-right plan wastes a call and fails a job for no reason." The plan then gets team identity stamped onto it — cast members belonging to a focused team are re-dressed in that team's kit, overriding whatever the model said.

4–5  Shot writer & casting — shotwriter.py catalog.py research.py

The shot writer turns each scene's fields into cinematography prose — one call per job, a fraction of a cent, and it reads better to a video model than labelled fields. Guardrails are appended deterministically afterwards, "because a model that can delete a guardrail eventually does."

Casting resolves each cast member against the catalog. If someone is off-catalog and their name reads like a real person, one web-search call fetches their real look, club, squad number and kit before any image money is spent — then the character is persisted, and (with CATALOG_AUTOGEN_REFS=on) two reference stills are generated on the spot so they render consistently in this job and every future one.

6  Keyframes — the cheap gate

The economic argument: a still costs ~$0.05, a clip costs 20×+ more. So every quality decision happens on the still. Up to 3 attempts per scene; each rejected attempt escalates the prompt with a correction targeting what actually failed.

Scene 0 renders first, alone — its keyframe becomes the "world anchor" reference attached to every later scene, on top of identity stills for each visible cast member. Before that, reviewed clips drifted between scenes (a kit changing clubs, a crowd changing colours) because scenes shared only prompt text. The rest render concurrently, capped at max(2, min(4, cpus×2)).

The review gate (review.py, cheap vision model) splits verdicts into hard and soft. An early binary version failed every frame, because near-perfect hands are rare and it treated odd fingers the same as a brand logo.

VerdictTriggersEffect
hardgarbled lettering · collage/split-screen · not photoreal · severe anatomyRegenerate with an escalated prompt
softodd hands · minor anatomy · busy lower quarter · reviewer doubts the subjectNote it and move on

Note what is no longer a failure: visible text and real logos. A measured A/B found the model renders "SPURS 1" cleanly when asked for the real kit, and jersey-shaped gibberish when told a jersey must carry no lettering. Banning text caused the garbling it was meant to prevent. The gate now judges the quality of lettering, not its presence.

7  Animate — the expensive stage

Each approved keyframe is submitted to OpenRouter's async video endpoint as the first frame, with the motion prompt and the scene's duration. Audio is generated natively in the same pass — there is no separate TTS step. Poll every 8s, up to 900s. Scenes animate concurrently.

If it fails or the budget is exhausted: Ken Burns push-in on the still. If that fails too, the scene is dropped and the job continues with what's left.

8–9  Assemble & validate — media.py

  • Give every clip an audio track (silent if needed), then ask whether they already agree. They usually do — same generator, same job — so the video streams are stream-copied instead of re-encoded. That's the expensive half of assembly skipped.
  • Caption windows come from each delivered clip's real probed duration, not the planned one — generated clips routinely run long or short.
  • concat → brand (captions + watermark + optional AI disclosure burn-in) → end_card. Branding and the outro are cosmetic: on failure the video ships without them rather than not at all.
  • Validate probes the final file: duration > 0, dimensions match the tier, audio present. Then a poster frame is extracted at the midpoint.
  • Delivery is at the generator's native size — 720×1280, not upscaled to 1080×1920. Measured on the droplet: 4.9s → 3.0s per clip, and Instagram accepts 720×1280 Reels natively.

Two-phase execution: script approval

With SCRIPT_APPROVAL=on (the default), run_clip_job runs in two distinct phases. Phase 1 fetches the Storyline Pack, writes the full script, stores it on the clip row, and parks at script_ready — spending only text pennies. The user reads every shot and every line, edits them, approves or regenerates. Phase 2 renders the approved plan verbatim, never re-planning.

The daily spend gate applies to Phase 2 only — writing a script costs pennies and must never be refused by the video budget. Rejected drafts accumulate in script_history (capped at 10) and the user's feedback is folded into the rewrite prompt so the next attempt is genuinely different, not a rewording.

10 Catalog

How real athletes get rendered consistently

The catalog is two layers, merged at read time:

  • Curated JSON in app/video/catalog/ — ships with the code. characters.json (look, wardrobe, voice, aliases, teams, reference images) and teams.json (colour palettes, jersey description, venues, associated players).
  • DB rows in catalog_characters — written at runtime by auto-research and by the admin catalog page. These override the JSON entry with the same id, so an admin can edit or retire a curated character without a deploy.

At runtime:

  1. Focus detection scans the take for names and aliases (with surname matching and near-misspelling tolerance).
  2. The planner receives the roster with focused players first — it reliably leans on whoever is listed first — plus the focused team's palette and venues.
  3. Cast on a focused team get re-dressed in that team's jersey_description.
  4. select_references picks up to two stills per person — a face reference for close-ups, full-body otherwise — attached as identity anchors to the image call.
The identity insight

Reference stills are AI-generated by the same image model that renders keyframes — never real photos. That's legal simplicity, wardrobe control, and visual consistency in one decision. And no stills is fine: a famous name renders accurately from text alone. The stills exist to pin the less famous and to keep a person identical across shots.

11 Prompting

Four rules learned from real renders

Every one of these was a shipped defect first. All four are guarded by tests, and every prompt in the system is catalogued in prompt_registry.py (run python -m app.video.prompt_registry).

1 · Name the person, and demand legible lettering

Removing the name to suppress on-screen text also removes the likeness — an early render replaced a recognisable player with a generic stand-in that way. And telling a model a jersey must carry no lettering doesn't remove lettering, it degrades it into gibberish ("RUACIS" where "SPURS" belonged). Ask for the authentic kit, by team, with name and number spelled out.

2 · Job style may only add to the bible

style_for() used to read plan.style or STYLE_BIBLE — so a model-authored style line silently replaced the bible, and with it the only mention of "photoreal". A scene rendered as an isometric cartoon inside an otherwise photographic video. The PHOTOREAL clause is now separate, non-overridable, and opens and closes every image and motion prompt.

3 · No text-bearing props

Newspapers, phones, screens, signs, whiteboards — anything a camera would show writing on forces the model to render lettering nobody named, which comes back as alien script. Unnamed surfaces (ad boards, scoreboards, signage) are explicitly required to stay plain or out of focus. This cost two consecutive keyframe rejections in a real run.

4 · Consecutive scenes never share a speaker

The video generator gives the same character a different voice in every clip, and voice pinning isn't available. Alternating speakers means no character is ever heard twice, so the drift has nowhere to show. Enforced in planner._repair. Load-bearing until voice pinning exists.

The planner's system prompt, in brief

It opens by defining the role — "an Instagram Sports Banter Reels specialist" — then states what makes Reels work: reach comes from retention and shares, both decided in the first second, so the funniest visual must be on screen immediately; every later scene must raise the premise rather than restate it; the last line is the one that gets quoted. Comedy comes from a specific absurd situation the camera can see, never from wordplay.

Then the hard rules, which are the interesting part:

  • Keep the user's stance. Sharpen and exaggerate; never reverse or soften. (This is BR-04 and business rule 3.)
  • ONE WORLD. Every shot's venue is the same text word for word. Props that exist in one shot exist in all later shots, described identically. Light and weather never change.
  • Varied shot lengths like a real edit — one 5–8s anchor carrying the dialogue, the rest 2.5–4s cutaways. Cutaways may be silent.
  • At most 2.2 words per second of a shot's length, so a line is speakable inside its clip.
  • If the take is a brief, it's requirements, not inspiration. Named people must appear as themselves; a requested ending becomes the payoff verbatim.
  • The roster is not a limit. A named real figure who isn't on it gets cast anyway — never swapped for a lookalike ("Ronaldinho" is not "Ronaldo").
  • Managers wear staff clothing, never a numbered player shirt. (A rendered Arteta-as-player was the bug that added this.)
12 Queue

A Postgres table is the job queue

Generation used to run on a daemon thread inside the API process, so a deploy or crash mid-job lost the work silently: the clip stayed pinned in a generating status forever and the user's allowance was gone. Now a job is a row.

Nothing is lost

Deploying the API, restarting a worker or losing the box leaves the row queued or reclaimable.

Nothing runs twice

enqueue refuses a second live job for a clip. A double-click or retried POST cannot bill a render twice.

Nothing gets stranded

A heartbeat refreshes locked_at every 30s. A lock older than 10 min is reclaimed.

SELECT * FROM jobs
 WHERE status = 'queued' AND run_after <= now()
 ORDER BY run_after, created_at LIMIT 1
   FOR UPDATE SKIP LOCKED;   ← several workers poll the same table,
                                 each takes a different row, none block

The worker process

python -m app.worker, run by systemd. The loop is deliberately dull: claim one job, run it, mark it, repeat, sweeping for stale locks every 60s. On SIGTERM it stops claiming and puts the in-flight job back without counting an attempt — the interruption was our doing, not the job's fault. systemd waits up to 180s for that.

The unit file is worth reading for the operational scars: Nice=15, CPUWeight=20, MemoryMax=600M. One render pins a core for minutes; on a single-vCPU droplet that made the API stop answering entirely — measured at load 12 with 29 MB of RAM free while a clip assembled. The worker must always lose to request handling. And Environment=PATH= lists the system directories explicitly, because systemd replaces PATH rather than extending it, and without /usr/bin every render fails immediately on the missing-ffmpeg check.

Housekeeping cron

python -m app.services.housekeeping, hourly. Purges expired scratch files and — crucially — fails any clip stuck in a generating status past 45 minutes, with an honest message. Without it a user watches a spinner forever with no way to retry, because the clip never reaches failed.

Two hard-won details

The final MP4 must be publicly readable. Instagram fetches it by URL at publish time and cannot present credentials. UUID-based unguessable keys are the protection.

Public cache TTL is 300 seconds, deliberately. Deleting an object removes it from storage immediately, but Cloudflare keeps serving a cached copy until it expires — measured: after delete_prefix the bucket listing was empty while the public URL still returned 200 with cf-cache-status: HIT. Supabase exposes no purge API, so the TTL is the window in which a deleted video stays fetchable. Five minutes trades a little egress for a deletion that means something.

Upload failure has a floor. If storage is unreachable even after retries, the finished MP4 is copied into MEDIA_DIR and served from the droplet, with a loud log.error. A ready clip with no URL renders as a phantom failure in the UI — observed in production, hence the fallback.

Deleting a clip deletes the bytes. Dropping only the row would leave the video publicly fetchable at its URL forever — a deletion that does not delete.

14 Spend control

Three independent ceilings

This system spends real money per request. There are three separate brakes, and an operator kill switch.

Per job$14.00MAX_JOB_COST_USD

A shared thread-safe _Ledger — charge() is atomic, so two concurrent scene workers can't both see room for the last dollar. Past it, the pipeline degrades to stills rather than exceeding. Sized for the dearest legitimate job (30s at 1080p) so it only catches runaways.

Rolling 24h$25.00MAX_DAILY_SPEND_USD

Summed from clips.cost_usd. Checked before a render starts — refusing up front is much kinder than dying halfway and leaving a half-paid-for clip. If the counting query itself fails, it allows the job: refusing everything because a count broke is worse than briefly overspending.

Kill switchoffgeneration_paused

A runtime setting the admin console flips. Refuses every new real generation outright, before the cap arithmetic. Both caps are also DB-backed runtime settings now — changing them no longer requires SSH and a restart.

Why the daily cap exists

"MAX_JOB_COST_USD stops one runaway clip. It does nothing about the case that actually empties an account: an ordinary day of ordinary users. At roughly $2.40 a clip, two people using their free allowance costs more than $20." There was a real August incident where the OpenRouter balance went negative and the first symptom was every generation failing — which is why the admin dashboard now has a provider-balance card and alert strip.

15 Billing

Stripe is the ledger; we store entitlement

Four design principles are written into routers/billing.py:

  • Stripe is the ledger. Invoices and charges are never mirrored locally — the DB stores only users.plan + subscription pointers, plus an audit log of processed webhook deliveries.
  • Webhooks are triggers, not truth. Stripe delivers at-least-once and in any order, so no handler trusts the event payload for state. Every billing event triggers a fetch of the customer's current subscriptions and convergence to that. Replays and reordering are harmless.
  • Idempotent transitions. Analytics events fire only on actual plan transitions. The stripe_events row is written after processing, so a mid-processing crash lets Stripe's retry reprocess safely.
  • One live subscription per user. If a checkout race ever produces two, sync_subscription_state cancels all but the newest. A user can never be double-billed.

Flow: POST /billing/checkout creates a hosted Checkout session and returns a URL the browser redirects to. Webhooks at {API_BASE_URL}/billing/webhook drive plan state. POST /billing/portal opens Stripe's own billing portal. Cancellation sets cancel_at_period_end — downgrades apply at period end and videos are never deleted for billing reasons.

With STRIPE_* unset, /checkout returns 503 and the frontend transparently uses /billing/upgrade, a dev mock that just flips the plan. That mock refuses to run once Stripe is configured.

OAuth and tokens

Instagram Business Login with scopes instagram_business_basic,instagram_business_content_publish. The OAuth state is itself a signed 15-minute JWT carrying the user id and the return path — so the callback can't be forged and onboarding progress isn't lost across the redirect (BR-14). Authorization code → short-lived token → long-lived 60-day token → identify the account.

Long-lived tokens do not renew themselves. maybe_refresh_token rolls any token inside its last 15 days, and it's called on every socials read and before every real publish — so any account used at least once in two months never lapses. An expired, unrefreshable token flips the account to revoked so the UI prompts a clean reconnect instead of failing publishes.

Two lessons in the code

  • The public URL bug. An earlier version rebuilt the video URL as {API_BASE_URL}/media/{filename}, which worked only while every clip was the demo file. Once clips moved to object storage the real key became users/{uid}/clips/{cid}/final.mp4, so the rebuilt URL resolved to /media/final.mp4 — a 404. Instagram fetched nothing and reported it as "could not process the video", which sent everyone looking at the encoding.
  • Localhost always simulates. Meta downloads the video from a public URL; with a localhost API_BASE_URL that's unreachable, so local dev simulates even for genuinely connected accounts.

Publishing is always an explicit per-clip action with an editable caption — nothing ever posts automatically (BR-13). A failed publish retries free and never regenerates the video. Only Instagram is connectable; other platforms are visible but return platform_locked.

Demo markers

[mock] in the take

Simulates a whole run — real stages, real pacing, nothing generated — whatever PIPELINE_MODE is set to. The one intended way to demo on production without spending.

Forces a failure at the scene stage (or a failed publish). Demonstrates the free-retry path on demand.

Three rules that make markers safe in production
  • The marker is stripped from the stored take, so it can never surface in the video, the captions, or a published Instagram caption.
  • The clip is flagged is_simulated.
  • Simulated clips do not consume the monthly allowance — charging for a clip generated from someone else's footage would be indefensible.

Measured, not estimated: ~$0.148/sec at 720p and ~$0.256/sec at 1080p, all-in.

Add ~25% for keyframe retries. Latency: roughly 4.5 minutes for a 15s clip.

The still-vs-clip ratio is the whole economic argument for the architecture: a still costs ~$0.05, a clip costs ~$1.12 for 8 seconds — about 22×. Every quality decision therefore happens on the still, and motion is only bought for frames that already passed review.

PRICING.md describes a planned credits model (4 credits/sec at 720p, 7 at 1080p; ~$0.10 retail per credit against ~$0.04 cost, so ~60% margin) — but note this is a designed system, not a shipped one: the admin console explicitly reports credits: enabled: false, and the live product still counts whole videos per month.

Production

What to watch

Not CPU. /health/ready reports queue depth: a rising queued with a flat running means no worker is alive, and the API stays perfectly healthy while every clip waits forever. Alert on queued > 5 for 10 minutes.

24 Gaps

Where the docs and the code disagree

Worth knowing before you trust a markdown file over a module.

contradiction  Jersey lettering

catalog/README.md and VIDEO-GENERATION-PLAN.md §5.5 still state the old rule: "wardrobes never carry lettering… every jersey string ends with no logos, no numbers, no lettering." The code and the data now do the exact opposite — characters.json asks for "the authentic Spurs jersey with the crest and the number 1, crisp legible lettering", and prompts.py documents the A/B that reversed it. The code is current.

stale  "Video generation is dummy"

The root README.md, backend/README.md and main.py's FastAPI description all say generation runs in dummy mode pending a provider bake-off. It doesn't — PIPELINE_MODE defaults to real, and ROADMAP.md lists the real pipeline as shipped.

stale  "Not built yet" list

app/video/README.md lists the durable queue, object storage, DB provenance and parallel scenes as unbuilt. All four now exist (jobs table, SupabaseStorage, clips.provenance, ThreadPoolExecutor).

stale  Tones and models

frontend/README.md says tones are "exactly Funny / Savage / Hype" — Bold was added (BRD v2.1). VIDEO-GENERATION-PLAN.md §3 names gpt-4o-mini as the planner; the default is now gpt-4.1. MAX_JOB_COST_USD is documented as 8.0 in three places and is 14.0 in config.py.

designed, not shipped  Credits

PRICING.md v2.0 describes a full credits economy as the pricing model. /admin/credits returns enabled: false and nothing else in the codebase assumes credits exist. Allowance is still whole videos per month.

known limit  Real open items

From the BRD's own §9 and the roadmap: Meta App Review is not complete, so arbitrary users can't yet connect Instagram. Voice pinning is unavailable, which is why the alternating-speaker rule is load-bearing. Multi-model routing (the biggest cost lever) is October work.

Reading order, if you're new

BRD.md for what it must do → backend/app/models.py for the shape of the data → backend/app/routers/clips.py for the main user flow → backend/app/video/runner.py for how a video is actually made → frontend/src/state/AppContext.jsx for how the client sees all of it. The comments in video/ are unusually dense and unusually worth reading; most of them record a specific bug that shipped.
