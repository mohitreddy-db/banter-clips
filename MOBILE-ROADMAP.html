01 · The reframe

The product is the API, not the website

Get this straight before anything else, because it determines how much work there is.

backend/app/ holds the entire product: accounts, plans, the durable job queue, the video pipeline, Instagram publishing, spend caps, billing. frontend/src/ holds a React SPA that calls it over HTTP and draws pictures.

A Flutter app is a second thing that calls it over HTTP and draws pictures. Nothing in the backend needs rewriting. Roughly four small additions land there over the whole project — a deep-link redirect, a device-token endpoint, optional push hooks, optional IAP receipt verification — and that is all.

The consequence

If you had to build the API too, this would be a year of work. Because it exists, sixteen weeks to a shipped Android app is realistic for a beginner. Almost everything below is about UI, platform configuration, and store policy — not architecture.

04 · Blockers

Four problems the web version never had

Read these before planning anything. Each has bitten real projects late, when it was expensive. Two are business decisions, not code.

Blocker 1 · You cannot build iOS on Windows

Compiling for iOS requires Xcode, which is macOS-only. You are on Windows 11, so plan around it explicitly rather than discovering it in month three.

  • Now: develop on Windows, target Android only. The Dart code is identical either way.
  • For iOS, pick one: a Mac mini (~$599, the cheapest real option); a cloud CI service like Codemagic or a GitHub Actions macos-latest runner, which can build and ship to TestFlight without you owning a Mac; or a rented cloud Mac.
  • Honest caveat: CI-only iOS works for building and releasing, but debugging an iOS-specific layout or permission bug with no Mac in front of you is miserable. Budget for a Mac before iOS launch — not before Android launch.

Apple Developer Program is $99/year. Google Play is $25 once — register that one early, because new Play accounts face a closed-testing requirement (12 testers for 14 days) before public release, and that clock is worth starting now.

Blocker 2 · Your Stripe checkout will get the app rejected

Creator at $9.99/mo is a digital subscription consumed inside the app. Apple (Guideline 3.1.1) and Google both require that to run through their billing, which takes 15–30%. A Stripe Checkout page opened in the app is a straightforward rejection.

UNIT-ECONOMICS.md already flags Creator as margin-negative above four videos a month. A store cut on top of that is a pricing decision to make before you build the paywall, not a surprise to absorb after. Three legitimate paths:

  • Native IAP — implement in_app_purchase, raise the mobile price to absorb the cut, reconcile store receipts with users.plan server-side. Best UX, most work, worst margin.
  • Reader-style split — the app ships free-tier only and upgrading happens on the website. Safe and cheap, but conversion drops, since you can't freely advertise it in-app on iOS.
  • Free-tier-first launch — v1 is a companion app for existing users, with a "manage your plan on banterclips.com" line in Account. Ships fastest and defers the whole problem to v2. For a first app, this is the one I'd pick.

Blocker 3 · Instagram OAuth needs a backend change

GET /socials/instagram/oauth-url mints a state JWT holding a next path and rejects anything not starting with /. Correct for a website; wrong for an app, because a phone has no browser tab to return to.

The mobile flow opens Meta's consent page in a system browser sheet (flutter_web_auth_2, which wraps ASWebAuthenticationSession on iOS and Custom Tabs on Android), then regains control through a redirect your app owns:

  • Register a custom scheme — banterclips://oauth/instagram — with an Android intent filter and an iOS CFBundleURLTypes entry.
  • Add that URI to the Meta app's valid OAuth redirect list, alongside the web one.
  • Backend: allow that specific scheme in next, allowlisted explicitly. Do not loosen the check to accept arbitrary URLs — that is an open-redirect hole.

Google sign-in has the same shape of problem: it needs its own Android OAuth client keyed to your signing SHA-1 and an iOS client keyed to your bundle ID. Neither reuses the web client.

Blocker 4 · Long jobs don't survive backgrounding

Studio.jsx polls every second while a video renders; Clips.jsx every 1.5s. A browser tab can do that forever. A phone cannot — iOS suspends your process seconds after the user leaves, and Android kills it under memory pressure. Generation takes minutes.

  • Foreground: keep polling but slow it to 2–3s, and stop it when the app backgrounds. Use WidgetsBindingObserver for lifecycle events, or you will drain batteries and leak timers.
  • Background: the real answer is a push notification when the job completes — Firebase Cloud Messaging reaches Android directly and iOS via APNs. Needs a POST /me/devices endpoint and a hook in the worker.
  • v1 shortcut: ship without push. Refetch on resume and say "this takes a couple of minutes — we'll have it ready when you come back". Honest, and it works.

06 · Phase 1

Set up the machine and the repo

Week 1 · mostly downloads

Toolchain

  1. Install the Flutter SDK (stable channel) and put it on your PATH.
  2. Install Android Studio — you need it even if you write code in VS Code, because it owns the Android SDK, the emulator and the platform tools.
  3. In its SDK Manager, install the latest SDK platform and the command-line tools. Create one emulator (a Pixel image).
  4. Run flutter doctor and fix every line until only the iOS/Xcode entries stay red. Accept licences with flutter doctor --android-licenses.
  5. In VS Code, install the Flutter and Dart extensions. That is the whole editor setup.
  6. Verify the loop: flutter create hello, flutter run, press r to hot-reload. If that works, your environment is done.

Repo

Your folder is banter-clips-main — an unzipped GitHub download with no git history, so you currently cannot branch or revert. Fix that before writing any code: 

# clone properly, then work on a branch
git clone https://github.com/<you>/banter-clips.git
cd banter-clips
git checkout -b mobile-app

The repo already has a clean convention: frontend/ and backend/ are independent projects with their own dependencies and .env. Follow it exactly and add a sibling: 

banter-clips/
├── frontend/   React SPA        → Vercel
├── backend/    FastAPI          → droplet
├── mobile/     Flutter app      → Play Store / App Store   ← new
└── deploy/

Create it with:

flutter create --org com.banterclips --project-name banterclips mobile

Get the org string right now

--org becomes your iOS bundle ID and Android package name. Changing it after a store submission means a new listing and losing your users. Decide once, here.

07 · Phase 2

Learn enough Dart and Flutter

Weeks 1–3 · the only pure-study phase

React transfers more than you'd expect: widgets are components, setState is setState, and composition beats inheritance in both. Don't take a 40-hour course. Learn this specific list, then start building and look things up as you hit them.

Dart — about a week

  • Null safety. String vs String?, and the ?. ?? ! operators. The biggest difference from JavaScript, and 80% of your early compiler errors.
  • async / await and Future. Nearly identical to JS promises. Your whole app is API calls, so this must become automatic.
  • Stream. The thing JS doesn't really have. Used for auth state and anything emitting over time.
  • Classes, named and factory constructors, final. Dart is class-based in a way React isn't.
  • Skip for now: isolates, mixins, generics beyond basic use.

Best source: the official Dart language tour. Short and unusually well written.

Flutter — about two weeks

  • Widget tree fundamentals — StatelessWidget vs StatefulWidget, and what build() actually does.
  • Layout — Column, Row, Expanded, Flexible, Stack, Padding, SizedBox. It's flexbox with different names. Learn to read "RenderFlex overflowed by 37 pixels"; you'll see it daily.
  • Scrolling — ListView.builder, SingleChildScrollView, CustomScrollView.
  • Navigation — learn Navigator.push to understand the model, then move to go_router and stay there. It's the closest thing to the react-router you already use.
  • Theming — ThemeData, ColorScheme, TextTheme. Phase 08 depends entirely on this.
  • State — start with setState. When you outgrow it, adopt Riverpod. Your AppContext.jsx maps almost one-to-one onto a set of providers.

Best sources: the official Flutter codelab, then Flutter Widget of the Week on YouTube — each video is 60 seconds; watch them while eating.

On "getting good at Android and iOS"

Flutter deliberately hides the platforms — that is the point of it. To actually learn them, spend real time in mobile/android/ and mobile/ios/ instead of treating them as generated noise. You'll meet AndroidManifest.xml, Gradle, Info.plist, signing keys, permission strings and provisioning profiles for real in phases 11 and 12. That is where the native knowledge is, and it's the part that transfers when you later pick up Kotlin or Swift.

08 · Phase 3

Turn the Figma file into a design system

Week 4 · one focused week

The instinct is to open the first screen and start building it. Don't. Extract the system first — colours, type, spacing, components — so that screens become assembly rather than invention. This is the difference between an app that looks designed and one that looks like eleven separate afternoons.

Avoid Figma-to-Flutter export plugins

They emit thousands of lines of absolutely-positioned, unnamed widgets that no human can maintain and that break on every screen size but the artboard's. You'll spend longer untangling the output than writing it yourself, and learn nothing in the process.

The method

  1. Open Figma in Dev Mode. It gives exact hex values, font sizes, weights, line heights and spacing per element. Figma px map 1:1 onto Flutter logical pixels, so a 16px gap is SizedBox(height: 16) — no conversion maths.
  2. Audit the tokens. Walk the whole file and write down every distinct colour, text style, corner radius and spacing value. Expect near-duplicates (#1F1F1F and #202020). Collapse them — six greys beat nineteen.
  3. Write lib/theme/. Three files: colors.dart (a ThemeExtension holding brand colours), typography.dart (a TextTheme), app_theme.dart (the ThemeData assembling them). Fonts live in assets/fonts/, declared in pubspec.yaml.
  4. Build the component catalog. Every Figma component becomes one widget in lib/widgets/ — primary button, secondary button, text field, chip selector, clip card, loading state, empty state, error banner, bottom sheet — each with all its states: default, pressed, disabled, loading.
  5. Make a gallery screen. A throwaway route rendering every widget in every state on one page, compared side by side with Figma. Catches in an hour the inconsistency you'd otherwise notice in week nine.
  6. Then build screens. Each should be mostly composition of things that already exist.

Two things Figma won't tell you

  • Safe areas. Figma artboards are flat rectangles; real phones have notches, Dynamic Islands and gesture bars. Wrap screen bodies in SafeArea and test on a notched device.
  • The keyboard. Studio is a big text field, and the keyboard eats half the screen when it opens. Scaffold(resizeToAvoidBottomInset: true) plus a scrollable body is the fix — a bug you only find by typing on a real device.
09 · Phase 4

The API client and authentication

Weeks 5–6 · the true foundation

Everything else sits on this layer. Build it properly and screens are easy; build it badly and you fight it for months. Your reference is frontend/src/lib/api.js — port it method for method.

Models first

Unlike JavaScript, Dart wants typed objects. Write a class per API entity — User, Clip, ScriptLine, SocialAccount, Usage, Publish — each with a fromJson factory. Use freezed and json_serializable to generate the boilerplate, checking each response shape in /docs as you go. Tedious for two days, then permanently valuable: the compiler starts catching your typos.

The client

Use dio rather than bare http, because interceptors let you attach the bearer token and translate errors in one place — mirroring the request() helper in api.js: 

// lib/api/client.dart — the shape to aim for
class ApiClient {
  final Dio _dio;

  ApiClient(this._dio) {
    _dio.interceptors.add(InterceptorsWrapper(
      onRequest: (options, handler) async {
        final token = await TokenStore.read();
        if (token != null) options.headers['Authorization'] = 'Bearer $token';
        handler.next(options);
      },
      onError: (e, handler) {
        // 401 → clear token, bounce to sign-in
        // backend sends {detail: {code, message}} — surface `message` to the UI
        handler.next(e);
      },
    ));
  }

  Future<List<Clip>> listClips() async { ... }
  Future<Clip> createClip({required String take, required String sport,
      required String tone, int duration = 15, String resolution = '720p'}) async { ... }
}

Match the error contract exactly. The backend returns {"detail": {"code": ..., "message": ...}} and api.js unwraps that into an ApiError. Do the same in Dart, so the UI can switch on code — that is how you show "you've used all 5 clips this month" instead of "Request failed (403)".

Auth — mirror the web flow exactly

The site does a two-step dance, and mobile does the identical one:

  1. Sign in against Supabase with supabase_flutter (email+password, Google, or magic link).
  2. POST /auth/supabase with the Supabase access token. The backend verifies it against Supabase Auth, finds or creates the user row, and returns its own 30-day session JWT.
  3. Every later request carries that backend JWT — not the Supabase one.

Do not use SharedPreferences for the token

The web keeps that JWT in localStorage. The mobile equivalent is flutter_secure_storage, which uses the iOS Keychain and Android Keystore. shared_preferences is plaintext on disk and readable on a rooted device. A 30-day session token belongs in the secure store.

Environment config

Mirror the .env.example convention. Flutter's version is compile-time: flutter run --dart-define=API_URL=http://10.0.2.2:8000, read back via String.fromEnvironment.

10.0.2.2, not localhost

10.0.2.2 is how the Android emulator reaches your host machine's localhost. Inside the emulator, localhost means the emulator itself. This confuses everyone exactly once.

Prove it before building any UI

Write one ugly debug screen with four buttons: sign in, fetch /me, list clips, create a clip. No styling at all. When all four work against your local backend, the foundation is real and phase 10 is mostly layout.

10 · Phase 5

Build the screens

Weeks 7–10 · the bulk of the work

Build in this order. Each screen unblocks the next, and the sequence keeps you always able to demo something end to end — which matters more than you think when motivation dips in week eight.

  1. Sign in / sign up / reset password. Wire up the phase-09 auth flow with real error states. Add an auth gate at the router level: go_router's redirect sends signed-out users to /sign-in, replacing the route guards in App.jsx.
  2. App shell. A BottomNavigationBar with three tabs — Create, Clips, Account. This replaces the web's header nav in AppShell.jsx; phones use bottom tabs because thumbs live at the bottom of the screen.
  3. Onboarding. Small, skippable, PATCH /me/preferences. A gentle warm-up before the hard screen.
  4. Studio, part one — the take. Text field, sport/tone/duration/resolution pickers, the ✨ variations button (POST /clips/enhance-take, with round incrementing on each press), and the trending feed (GET /clips/trending?sport=). Gate 1080p and 30s behind Creator, exactly as the web does.
  5. Studio, part two — script review. Port the behaviour of ScriptView.jsx and ReviewStep.jsx: edit lines, regenerate with feedback, approve. Nothing renders or costs money until approval — preserve that rule precisely.
  6. Studio, part three — generation. Staged progress with elapsed time, polling GET /clips/{id}. Apply the lifecycle handling from blocker 4 here.
  7. Clip preview and publish. video_player plus chewie for controls. Vertical 9:16 wants a full-bleed player, not a letterboxed rectangle. Then caption suggestions and the Instagram publish flow with live status.
  8. Clips library. ListView.builder of clip cards, pull-to-refresh via RefreshIndicator, delete with confirmation, and share_plus for the native share sheet — the one genuinely better-than-web moment in the app.
  9. Account. Usage counter from /me/usage, plan display, Instagram connect/disconnect, preferences, legal links, sign out, delete account.

Habits worth forming now

  • Every async screen has four states — loading, empty, error, content. Build all four. The web version already has them; read the JSX.
  • Never leave a screen blank while loading. Skeleton placeholders read as fast; spinners read as broken.
  • Test on a real device weekly. Emulator performance and touch feel both lie to you.
  • Commit per screen. Small commits on mobile-app mean a bad afternoon costs an afternoon.
11 · Phase 6

Platform integrations

Weeks 11–12 · where you learn Android and iOS

Everything so far was Dart. This phase is native configuration — the part that makes you a mobile developer rather than a Flutter user. Expect it to feel slow, because it always does.

  • Deep links. Register banterclips:// in AndroidManifest.xml (an intent-filter) and Info.plist (CFBundleURLTypes), then wire the Instagram OAuth return from blocker 3. Optionally add App Links / Universal Links so banterclips.com/clips/123 opens the app — that needs a verification file served from your domain.
  • Google sign-in. Create the Android OAuth client with your debug and release SHA-1 fingerprints, plus an iOS client with the bundle ID.
  • Permissions and privacy strings. Saving a video to the camera roll needs NSPhotoLibraryAddUsageDescription in Info.plist, written as a human sentence, and scoped-storage handling on Android. Apple rejects missing or lazy usage strings.
  • Icon and splash. flutter_launcher_icons and flutter_native_splash generate every required size from one source image. Export a 1024×1024 icon from Figma.
  • Push notifications v2 OK — a Firebase project, google-services.json for Android, an APNs key uploaded to Firebase for iOS, plus POST /me/devices and a worker hook.

Two mistakes that cost a whole release

  • Forgetting the release SHA-1 for Google sign-in. It works perfectly in testing and fails for every real user, because the release build is signed with a different key.
  • Losing the Android upload keystore. Generate it, then back it up somewhere outside the repo. Lose it and you can never update that Play listing again — ever. Add it to .gitignore and never commit it.

Then: billing, per your blocker-2 decision

If you chose native IAP: create the subscription product in App Store Connect and Play Console, integrate in_app_purchase, and — critically — verify receipts server-side before flipping users.plan. Never trust the client's word that a purchase succeeded. Budget two weeks; it is fiddly and the sandbox environments are unpleasant. If you chose free-tier-first, this is one line of copy in Account and you skip the whole thing.

12 · Phase 7

Test, harden, and prepare the stores

Weeks 13–15

Testing that's worth your time as a beginner

  • Unit tests on the API client and any parsing or formatting logic — port the cases from frontend/src/lib/format.js.
  • Widget tests on the component catalog. Cheap, fast, and they catch regressions when you refactor the theme.
  • A manual matrix, which matters far more than coverage at this stage: small phone, large phone, notched phone, airplane mode mid-generation, backgrounding during a render, an expired session, a free user hitting the monthly cap, and a device with system font size at maximum.
  • Skip integration tests for v1. The return isn't there yet.

Store assets — start early, they take longer than you think

  • App icon; Play feature graphic (1024×500); screenshots at every required size for both stores — build these in Figma from real app captures.
  • App name, subtitle, description, keywords. SEO.md already has the positioning language; adapt it.
  • Privacy policy URL (you have one), plus a data safety form (Play) and privacy nutrition label (App Store). Answer honestly — you collect email, and you generate and store user content.
  • A working account for the reviewer. Both stores require test credentials for a login-gated app. Omitting this is the single most common cause of a first rejection.

Two review risks specific to this app

User-generated content. Your app generates AI videos of public figures. Apple's Guideline 1.2 requires UGC apps to have a content filter, a report mechanism, a block mechanism, and published terms. The AI-parody disclosure helps; a "report this clip" path and a stated moderation policy help more. Sort this before submitting, not after a rejection.

Minimum functionality. Guideline 4.2 rejects thin wrappers around a website. Yours won't be — it's native, with a real share sheet and video player — but keep webviews to the legal pages only.

13 · Phase 8

Release and iterate

Week 16 onward
  1. Android internal testing first — instant, no review. Get the build onto your own phone through Play.
  2. Closed testing — if your Play account is new, this satisfies the 12-testers-for-14-days requirement. Start it as soon as you have a usable build.
  3. TestFlight for iOS. Its review is lighter and faster than App Store review; use it to catch iOS-only issues before the real submission.
  4. Submit. Expect a rejection on the first attempt. It is routine, not failure — read the citation, fix precisely that, resubmit.
  5. Add crash reporting before launch, not after — Crashlytics or Sentry. Without it, a user's crash report is unactionable.
  6. Ship the deferred work: push notifications, then IAP if you deferred it, then whatever the first fifty users complain about.

One permanent consequence for the backend

Your backend and frontend auto-deploy from main, but mobile releases are gated by store review and users update on their own schedule. So the API can no longer make breaking changes freely — old app versions stay in the wild for months. Version your endpoints, or keep every change additive.

What to do this week

The plan above is sixteen weeks. Only the next five days are actually actionable, so here they are.

  1. Clone the repo properly and create the mobile-app branch. Your current folder has no git history, so you can't branch or revert today.
  2. Install Flutter and Android Studio. Get flutter doctor clean and run the counter app on an emulator with hot reload working.
  3. Register a Google Play developer account ($25). New accounts face the 14-day closed-testing requirement — start that clock now, in the background, while you learn.
  4. Read frontend/src/lib/api.js end to end and write out, on paper, the endpoints your v1 screens actually need. That list is your phase-09 checklist.
  5. Make the billing decision from blocker 2. It changes phase-11 scope by two weeks and your pricing by up to 30%, and it is far easier to decide now than to discover during a rejection.

The honest timeline

Sixteen weeks to a shipped Android app is realistic for a beginner at 15–20 hours a week, given that the backend already exists. iOS adds two to four weeks and a Mac. If you had to build the API too, this would be a year. That is how much of this project is already done.
