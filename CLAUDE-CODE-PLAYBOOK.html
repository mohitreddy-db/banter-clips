Building the app with Claude Code

The roadmap says what to build. This says how to actually get it built when Claude Code is writing most of the Dart. The short version: Claude Code writes, and you are the eyes — it cannot see the running app, and a UI project lives or dies on that one limitation. Everything below is built around it.

01 · The method

Who does what

Be honest about the split from day one. Most people waste weeks either doing work Claude Code could do in a minute, or waiting for it to do something it fundamentally cannot.

CLAUDE Does this genuinely well

  • Porting from a spec. Turning api.js into a Dart ApiClient is close to ideal work for it — the contract is fully written down.
  • Typed models from JSON. Reading your OpenAPI schema and emitting freezed classes.
  • Reading your React code and telling you what a screen actually does, in order.
  • Boilerplate-heavy native config — manifests, plists, Gradle — where the syntax is exacting and well documented.
  • Running and fixing flutter analyze / flutter test in a loop until clean.
  • Explaining errors. Paste a RenderFlex overflow and ask why, not just for the fix.

YOU Only you can do this

  • Look at the screen. Claude can launch the app; it cannot see it. This is the big one.
  • Tap through it. Touch targets, scroll feel, keyboard behaviour, whether it feels fast.
  • Compare against Figma. Only you can say "that padding is wrong".
  • Log into portals — Play Console, App Store Connect, Meta for Developers, Firebase, Supabase dashboard.
  • Plug in a phone, accept licences, click through Xcode signing.
  • Decide. The billing model, the scope cuts, the price. Claude will give you options; the call is yours.

The failure mode to avoid

Asking for three screens in one go, accepting the output because it compiles, and moving on. Six sessions later nothing renders correctly and you cannot tell which of six hundred edits broke it. Compiling is not working. A screen is done when you have looked at it running on a device — not before.

02 · The method

The build loop

Every piece of work runs through the same four steps. Two are Claude's, two are yours, and they alternate — that alternation is the whole discipline.

03 · The method

Session zero: set the repo up so Claude gets it right by default

Two hours here saves you from repeating yourself in every session for four months. Do it before phase 1.

1 · Write mobile/CLAUDE.md

Claude Code reads CLAUDE.md from the working directory and its parents, so a file at mobile/CLAUDE.md loads automatically whenever you work on the app. This is the single highest-leverage file in the project. Run /init to get a first draft, then make it say the things Claude cannot infer:

Type this

Write mobile/CLAUDE.md. It must cover: - The backend at api.banterclips.com is the source of truth and is NOT to be modified from this directory. frontend/src/lib/api.js is the API contract. - Never invent an endpoint. Check /docs or api.js. If it's not there, ask me. - Behaviour reference for any screen is the matching file in frontend/src/pages/. Read it before building. Do not port the JSX or Tailwind classes. - Never port frontend/src/admin/ — the admin console stays web-only. - All colours/type come from lib/theme/. No hardcoded Color(0xFF...) anywhere. - Commands: flutter analyze, flutter test, dart format lib/ - Run analyze and tests after every change and fix what they report. - Session JWT goes in flutter_secure_storage, never shared_preferences. - Ask before adding any new package to pubspec.yaml. Keep it under 60 lines. Be terse — it's read every session.

Keep it short on purpose

CLAUDE.md is loaded into context on every single session, so length has a real cost and long files get diluted. Rules that keep being ignored usually need to be fewer and sharper, not more detailed. Prune it monthly.

2 · Grant permissions once

By default Claude Code asks before each command. For a Flutter project that means approving flutter analyze forty times a day, and the friction makes you stop asking it to verify its own work — which breaks gate 3. Allowlist the safe, read-only, repeatable ones:

Type this

/permissions

Then add: Bash(flutter analyze:*), Bash(flutter test:*), Bash(dart format:*), Bash(flutter pub get:*), Bash(dart run build_runner:*)

Leave flutter build, git push, and anything touching backend/ or deploy/ asking for approval. Those are the ones where a mistake costs you something.

3 · Confirm the Figma connection

Figma's MCP server is already configured in this workspace, which means Claude can read your actual design file — exact variables, layout, and screenshots — instead of guessing from your description. Verify it before phase 3, not during:

Type this

/mcp

Then, with a frame URL from your file: Read this Figma frame and tell me what components and variables it uses. Don't write any code yet. <paste figma url>

4 · Add a screen-scaffolding command

You are going to build nine screens with the same structure. Put that structure in .claude/commands/screen.md once and invoke it with /screen clips instead of re-typing the conventions every time:

Type this

Create .claude/commands/screen.md — a custom slash command that takes a screen name as $ARGUMENTS and: 1. reads frontend/src/pages/<Name>.jsx for the behaviour 2. lists which existing widgets in lib/widgets/ it will reuse, and asks me before creating any new one 3. builds the screen with all four states: loading, empty, error, content 4. wires it into the go_router config 5. runs flutter analyze and fixes anything it reports It must stop and show me the widget-reuse list before writing code.

5 · Auto-format on save optional

A PostToolUse hook in .claude/settings.json can run dart format after every file edit, so formatting never shows up as noise in your diffs. Ask Claude to set it up — it knows the schema.

04 · The method

Session hygiene

Four habits. They are unglamorous and they are the difference between Claude Code speeding you up and Claude Code producing a mess you cannot debug.

  • One task per session, then /clear. A session that has been running for four hours across three features gives noticeably worse answers than a fresh one — old context crowds out the thing you actually care about. Finish the Clips screen, clear, start Account. Use /compact only when you genuinely need the history.
  • Plan mode before anything structural. Press Shift+Tab twice to enter it. Claude investigates and proposes without editing, and you approve or redirect before a single file changes. Use it for the API layer, routing, state management, and any refactor. Skip it for "build this one screen".
  • Point at files with @. @frontend/src/pages/Clips.jsx is precise; "the clips page" makes it go searching and sometimes guess. Precision in the prompt is the cheapest quality improvement available to you.
  • Commit at every green gate. When a screen renders correctly, commit. Small commits on the mobile-app branch mean a bad session costs a session, and git diff stays readable enough that you can actually review what changed.

Review the diff, don't just run the app

You are trying to learn mobile development, not just possess an app. Read every diff before committing. When something is unfamiliar, ask — "why a StatefulWidget here and not Stateless?", "what does this FutureBuilder do while it's waiting?" The answers are the actual education, and they cost you nothing but the asking.

05 · Phase 1

Machine & repo

Week 1 · mostly yours

Claude cannot install Android Studio or accept SDK licences for you. What it can do is diagnose, scaffold, and set up the repo conventions.

Type this

Run flutter doctor and go through the output line by line. For each problem, tell me exactly what to click or run on Windows 11 to fix it, and which ones I can ignore because I'm not targeting iOS yet.

Create the Flutter project as a sibling of frontend/ and backend/: org com.banterclips, project name banterclips, directory mobile/. Then show me what it generated and explain what android/ and ios/ actually contain — I want to understand those folders, not ignore them.

Add mobile/ entries to .gitignore: build artifacts, .dart_tool, any keystore or google-services.json. Explain each line.

Do this one yourself, first

Your folder is an unzipped download with no git history. git clone the repo properly and git checkout -b mobile-app before letting Claude write anything. Without git you cannot revert a session that went wrong — and one will.

06 · Phase 2

Learning Dart — with your own code as the textbook

Weeks 1–3 · don't delegate this one

This is the phase where it is most tempting to let Claude write everything and skip the learning. Resist that, because every later phase gets slower if you cannot read what it produces. The trick is to use Claude as a tutor working from code you already understand.

Type this

I know React and JavaScript well. Rewrite the request() helper from @frontend/src/lib/api.js in Dart, then walk me through it line by line — especially every place Dart's null safety forced a change JS didn't need. Don't simplify it; I want the real version.

Now quiz me. Give me five short Dart snippets from that file with a null-safety bug in each. Don't tell me the answers until I guess.

Explain Flutter's Column/Row/Expanded by rebuilding the layout of @frontend/src/components/AppShell.jsx as a Flutter widget tree. Map each Tailwind class to its Flutter equivalent so I can see the translation.

Learn the error messages, not just the fixes

When you hit "RenderFlex overflowed by 37 pixels" — and you will, weekly — paste it and ask "why does this happen and what are the three usual causes?" rather than "fix it". After the third time you will diagnose it yourself in five seconds, which is worth far more than three fast fixes.

07 · Phase 3

Figma → design system

Week 4 · the MCP earns its keep

Because the Figma MCP is connected, Claude reads your real file rather than your description of it. Insist on the audit step before any code — that is what stops you ending up with nineteen near-identical greys hardcoded across forty widgets.

Type this — in order, over 3–4 sessions

Read these Figma frames and produce a deduplicated token audit: every distinct colour, text style, corner radius and spacing value, with a note where two values are near-duplicates I should collapse. Output a table. Write NO code yet. <paste 3–4 frame urls>

Good. Now write lib/theme/ from that agreed token list: colors.dart as a ThemeExtension, typography.dart as a TextTheme, app_theme.dart assembling both into ThemeData. Light theme only for now.

Build lib/widgets/ from the Figma components in these frames — button, text field, chip selector, clip card. Every widget gets all its states: default, pressed, disabled, loading. Pull colours from the theme only. <paste component frame urls>

Now build a throwaway gallery screen at /debug/gallery that renders every widget in lib/widgets/ in every state on one scrollable page.

Then run it, screenshot the gallery, and put the screenshot next to Figma on your monitor. Everything wrong will be obvious in ninety seconds. Paste the screenshot back:

Type this — with the screenshot pasted in

Here's the gallery running next to the Figma frame. The card padding is too tight and the disabled button is the wrong grey. Fix both in the theme, not in the individual widgets.

Say no to Figma auto-export plugins

If Claude ever offers to generate widgets straight from a Figma export, decline. That output is thousands of lines of absolutely-positioned, unnamed widgets that break on any screen size but the artboard's — and you will learn nothing from code you cannot read.

08 · Phase 4

API client & auth

Weeks 5–6 · Claude's best phase

Porting a fully-specified contract into a typed client is the thing Claude Code does best, because nothing has to be invented. Use plan mode for the structure, then let it work.

Type this — plan mode on for the first two

Read @frontend/src/lib/api.js end to end. Produce a table of every endpoint: method, path, request body, response shape, and what the UI does with it. Flag anything the mobile app won't need. No code yet.

Fetch https://api.banterclips.com/openapi.json and generate freezed models from the ACTUAL response schemas — User, Clip, ScriptLine, SocialAccount, Usage, Publish. Do not guess field names; if the schema is ambiguous, list the ambiguity and ask me.

Now build lib/api/client.dart with dio. Mirror the error contract from api.js exactly: the backend returns {detail: {code, message}} and the UI switches on `code`. Add an interceptor that attaches the bearer token from flutter_secure_storage and clears it on 401.

Wire up auth, mirroring the two-step flow in @backend/app/routers/auth.py: supabase_flutter signs in, then POST /auth/supabase exchanges the Supabase token for our own 30-day session JWT. Store that JWT in secure storage.

Build one ugly debug screen — no styling at all — with four buttons: sign in, GET /me, list clips, create a clip. I want to prove the whole stack works before we build any real UI.

Watch for invented endpoints

This is the phase where a wrong guess is most likely and most expensive. If Claude produces a method you do not recognise from api.js, ask "which line of api.js or which entry in openapi.json is this from?" A real answer cites one. An invented one won't.

09 · Phase 5

The screens

Weeks 7–10 · one screen, one session

Nine screens, in the order given in the roadmap. Each gets its own session, its own gate-4 check, and its own commit. This is where the /screen command from session zero pays for itself.

Type this — per screen

/screen clips

Or the long form, if you skipped the custom command: Build the Clips library screen. - Behaviour reference: @frontend/src/pages/Clips.jsx — read it first and tell me the load order and every error state before you write anything. - Design: <figma frame url> - Reuse widgets from lib/widgets/. List what you'll reuse and what you think needs a new widget, and wait for me to approve the new ones. - All four states: loading (skeletons, not a spinner), empty, error, content. - Pull-to-refresh, delete with confirmation, share via share_plus.

Then gate 4, every time — no exceptions:

Type this — then actually look at the emulator

Run the app on the emulator and tell me the route to navigate to.

<screenshot pasted> The clip cards are right but the empty state is centred vertically and Figma has it at the top third. Also the delete confirmation has no cancel button. Fix both.

The Studio screen is three sessions, not one

Studio is roughly 40% of the app. Split it exactly as the roadmap does — take input, script review, generation progress — and gate each part separately. Asking for the whole thing at once produces something that compiles and that neither of you can debug.

Bring blocker 4 up explicitly

When you reach the generation screen, say so directly: "the web polls every second, but this is a phone — implement the polling with WidgetsBindingObserver so it stops on background and refetches on resume." Claude will happily port the web's 1-second interval verbatim if you don't mention it, and battery drain is invisible in an emulator.

10 · Phase 6

Native config

Weeks 11–12 · slow down here

Manifests and plists are exactly the kind of exacting, well-documented boilerplate Claude handles well — and also where a plausible-looking hallucinated key wastes an afternoon. Ask for explanation alongside every diff, both to catch errors and because this is the phase where you actually learn Android and iOS.

Type this

Add the banterclips:// custom URL scheme for the Instagram OAuth return. Show me the exact AndroidManifest.xml and Info.plist changes as a diff and explain what every element does BEFORE you apply anything. I want to understand intent filters and CFBundleURLTypes, not just have them.

Now the backend side: @backend/app/routers/socials.py rejects any `next` that doesn't start with "/". I need it to also accept exactly banterclips://oauth/instagram — as an explicit allowlist entry, not by loosening the check. Show me the diff and explain the open-redirect risk you're avoiding.

Walk me through generating the Android upload keystore. Explain what it is, why losing it is unrecoverable, where to back it up, and how to wire it into build.gradle without the password ever touching the repo.

Three things Claude must never touch

  • Your keystore, and its passwords. Generate it yourself. Never paste the password into a session.
  • .env, google-services.json, service keys. Confirm they are gitignored before they exist, not after.
  • Anything in backend/ or deploy/ without you reading the diff. That is live production serving real users.
11 · Phase 7

Test & store prep

Weeks 13–15

Tests are ideal delegation — tedious, mechanical, and machine-verifiable. Store policy is the opposite: Claude's knowledge of Apple and Google guidelines has a cutoff, and both change quietly. Use it to prepare, then verify against the live policy pages yourself.

Type this

Write unit tests for lib/api/ — happy path, 401, 403 quota-exceeded, network failure. Port the cases from @frontend/src/lib/format.js too. Then run flutter test and fix until green.

Write widget tests for everything in lib/widgets/, covering each state.

/code-review

/security-review

Draft the Play data-safety answers and the App Store privacy nutrition label from what the app actually collects — read @backend/app/models.py and the API client to ground it. Flag anything you're unsure about rather than guessing; I'll verify each answer against the live form.

Draft store listing copy — name, subtitle, description, keywords — using the positioning in @SEO.md and @BRD.md.

Verify policy claims yourself

Anything Claude tells you about Guideline 1.2, 3.1.1 or 4.2, or the Play closed-testing rules, is worth checking against the current policy page before you submit. It is a good drafting partner here and a bad final authority — the rules move, and the cost of being wrong is a rejected release.

12 · Phase 8

Release

Week 16 onward · mostly yours

Claude cannot log into Play Console or App Store Connect. What it can do is automate the build and upload path, which is also your route to iOS without owning a Mac.

Type this

Set up a GitHub Actions workflow that builds the Android app bundle on a tag push and uploads it to Play internal testing. Explain where each secret goes and why none of them belong in the repo.

Now add a macos-latest job for the iOS build and TestFlight upload — I don't own a Mac, so CI is my only path to iOS. Tell me honestly what this setup will and won't let me do without a Mac in front of me.

Add Crashlytics before we ship. Then explain how I read a crash report and get from a stack trace back to a line of Dart.

After launch, one rule changes permanently

Old app versions stay installed for months, so the API can no longer make breaking changes freely. Add that to backend/CLAUDE.md the day you ship: "a mobile client is in the wild — every endpoint change must be additive or versioned." Otherwise a routine backend edit will silently break users you cannot update.

13 · Staying safe

Where Claude Code will let you down

Knowing these in advance turns them from confusing failures into expected ones you route around.

LimitWhat it looks likeYour workaround
No eyes Confident "the screen is complete" for something that renders as a grey rectangle. Gate 4, every time. Screenshot back when wrong — it reads images well.
No hands on the device Cannot test scroll feel, touch targets, keyboard behaviour, or whether it feels fast. Your weekly real-device pass. Emulators lie about performance.
Policy drift Store guideline details stated confidently but slightly out of date. Draft with Claude, verify on the live policy page before submitting.
Package churn An API from an older version of a Flutter package; the code won't compile. Let flutter analyze catch it — gate 3 exists for exactly this.
Plausible invention An endpoint or field name that reads perfectly and isn't in your API. Ask it to cite the line in api.js or openapi.json. Real answers cite.
Context decay Late in a long session it forgets a convention it followed earlier. /clear between tasks. Put durable rules in CLAUDE.md, not in chat.
Over-eagerness You asked for one screen; it also refactored the theme and added two packages. Plan mode for anything structural. "Only touch these files" in the prompt.
14 · Staying safe

Guardrails

Five rules. They cost you seconds each and prevent the failures that cost days.

  1. Nothing enters pubspec.yaml without your approval. It is in your CLAUDE.md for a reason. Every package is code you didn't write, in a language you're learning, that can break on the next Flutter release.
  2. Secrets never enter a session. Not keystore passwords, not service keys, not the contents of .env. Reference the file by name; never paste its contents.
  3. backend/ and deploy/ are production. Read every diff there yourself. The mobile app is greenfield and forgiving; your live API serving real users is neither.
  4. Never commit what you haven't read. If a diff is too big to review, the task was too big. Split it and redo it.
  5. When it says "done", check. Compiling is not working; passing tests is not looking right. Gate 3 and gate 4 are different gates and you need both.
15 · Staying safe

Still learning, not just shipping

You said you want to get good at Android and iOS development. Shipping an app you cannot read would not be that, so build the learning into the workflow rather than hoping it happens.

  • Read every diff before committing. Non-negotiable. This alone is most of the education.
  • Ask "why this and not that?" — StatefulWidget vs Stateless, FutureBuilder vs a manual load, Riverpod vs setState. The tradeoff is the lesson; the code is just the artifact.
  • Type one screen yourself. Account is small and self-contained. Build it with no Claude assistance, then ask for a review. The gap between what you wrote and what comes back is the most precise measurement of your level you will ever get.
  • Live in android/ and ios/. Flutter hides the platforms; those folders are where they stop being hidden. Ask what each file does when you first meet it.
  • Predict before you run. Before gate 4, guess what the screen will look like and what will be wrong. You will be bad at this for a month and then suddenly good, and that transition is what expertise actually feels like.

A reasonable target

By phase 5 you should be able to read any screen file in your own app and explain what every line does. If you cannot, slow down — that is the signal to type more yourself and delegate less, not to push on faster.

16 · Start here

Your first session

In order. This is a real afternoon's work and it sets up everything after it.

  1. Clone the repo properly and git checkout -b mobile-app. Do this before Claude writes anything at all.
  2. Install Flutter and Android Studio, then let Claude walk you through flutter doctor line by line.
  3. Create mobile/ with the org string com.banterclips. Get it right the first time.
  4. Write mobile/CLAUDE.md using the prompt in section 03. This is the highest-leverage thing you will do all month.
  5. Set permissions so flutter analyze and flutter test run without asking. Gate 3 only works if it is frictionless.
  6. Register the Play developer account ($25) — the 14-day closed-testing clock should start now, in the background, while you learn Dart.
  7. Then start phase 2, and let Claude teach you Dart out of your own api.js.

The one sentence to remember

Claude Code writes; you look. Every habit in this document is downstream of that — one task per session so the writing stays reviewable, two gates so nothing is called done unseen, and every diff read so that in sixteen weeks you have both an app and the ability to maintain it.
